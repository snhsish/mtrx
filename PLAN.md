# PLAN.md

# mtrx

> **Local-first, unlimited, open-source telemetry and analytics for AI agents.**

mtrx is a self-hosted/local-first dashboard for collecting, normalizing, storing, and visualizing metrics generated by AI coding agents.

It is intended to be the **"htop/Grafana for AI agents"**: a local source of truth for what agents are doing, how much they are using, how they perform, and how they interact with a codebase.

The project has **no mandatory cloud service, no accounts, no pricing/billing system, no artificial usage limits, and no proprietary telemetry backend**.

---

## 1. Product Principles

### 1.1 Local-first

All telemetry is stored locally by default.

```text
Agent
  ↓
Local Collector
  ↓
Normalizer
  ↓
Local Event Store
  ↓
Analytics
  ↓
Local Dashboard

```

There must be no requirement for:

- account creation
- cloud authentication
- remote telemetry
- API keys
- hosted infrastructure
- external database
- internet access

The application must remain fully functional offline.

### 1.2 Absolutely FOSS

The complete core application must be open source.

No:

- proprietary telemetry backend
- closed-source collector
- cloud-only feature
- artificial usage limit
- paid dashboard tier
- token limit imposed by mtrx
- mandatory external service

The project should use a permissive FOSS license, preferably **Apache-2.0**.

### 1.3 Agent-agnostic

mtrx must not be designed around one specific AI agent.

Agents are adapters into a common telemetry model.

```text
Claude Code ─┐
Codex       ─┤
OpenCode    ─┤
Aider       ─┤
Gemini CLI  ─┤──> mtrx Event Model
Cursor      ─┤
Custom      ─┘

```

### 1.4 Raw data is sacred

Never throw away information merely because the dashboard does not currently use it.

Store:

1. normalized events
2. raw source events where practical
3. metadata needed to reproduce analytics

This allows future metrics to be added without recollecting historical data.

### 1.5 No "cost" dependency

Token consumption is a first-class metric.

Money is not.

mtrx should work equally well for:

- local models
- free APIs
- paid APIs
- self-hosted models
- unknown pricing
- custom providers

Pricing information must never be required for telemetry.

# 2. Goals

## Primary goals

- Collect telemetry from multiple AI coding agents.
- Normalize different agent formats into one event model.
- Track token usage.
- Track model usage.
- Track sessions.
- Track messages.
- Track tool calls.
- Track tool latency.
- Track errors and retries.
- Track file activity.
- Track git activity.
- Track agent performance.
- Store everything locally.
- Provide a powerful local dashboard.
- Support historical analytics.
- Support extensible adapters.
- Work offline.
- Provide a CLI and local HTTP API.
- Remain lightweight enough to run continuously.

## Secondary goals

- Import existing historical agent data.
- Detect installed agents automatically.
- Discover agent data directories.
- Support custom agents through an SDK.
- Export telemetry.
- Provide machine-readable APIs.
- Support multiple projects/repositories.
- Provide live dashboard updates.
- Make the system useful to developers as well as teams.

---

# 3. Non-Goals

mtrx is **not** intended to be:

- an AI coding agent
- an agent orchestrator
- a prompt marketplace
- a cloud analytics SaaS
- a billing platform
- a model router
- an LLM gateway
- a hosted logging service
- an AI model provider
- a replacement for Git
- a code editor

It observes agents; it does not control their behavior.

# 5. Technology Stack

## Backend

**Go**

Reasons:

- single binary
- low memory usage
- excellent filesystem support
- excellent concurrency
- easy distribution
- no runtime dependency
- ideal for long-running local daemons
- easy cross-compilation

## Database

**SQLite**

Use SQLite as the primary local event store.

Requirements:

- WAL mode
- foreign keys
- migrations
- prepared statements
- indexes for time-series queries
- batch inserts

Potential SQLite extensions should only be introduced when they provide clear value.

## Frontend

Use:

- HTML
- CSS
- vanilla JavaScript

The frontend should be embedded into the Go binary using `embed`.

No Node.js runtime should be required.

No npm runtime should be required.

No Vite/Next.js runtime should be required.

The build process may use tooling during development, but the distributed application must be a single executable with embedded assets.

## API

HTTP/JSON API.

Optional WebSocket/SSE layer for live updates.

# 7. Universal Event Model

The event model is the most important architectural component.

Every adapter converts agent-specific telemetry into these universal events.

## Event envelope

```go
type Event struct {
    ID        string
    Type      EventType
    Timestamp time.Time

    Agent     AgentRef
    Session   SessionRef
    Project   ProjectRef

    Payload   json.RawMessage

    Source    SourceRef
    Raw       json.RawMessage
}

```

Every event should have:

- unique ID
- timestamp
- agent
- optional session
- optional project
- event type
- normalized payload
- source metadata
- optional raw payload

# 9. Token Model

Token information should be represented independently of providers.

```go
type TokenUsage struct {
    Input       int64
    Output      int64
    CachedInput int64
    CacheWrite  int64
    Reasoning   int64

    Total       int64
}

```

Potential future fields:

```text
audio input
audio output
image input
image output
tool tokens
unknown tokens

```

Never assume every provider exposes every field.

Missing values should be represented as unknown/zero according to the event schema rather than fabricated.

# 11. Session Model

A session represents one continuous agent interaction.

```go
type Session struct {
    ID          string
    AgentID     string

    StartedAt   time.Time
    EndedAt     *time.Time

    InputTokens     int64
    OutputTokens    int64
```

# 16. Collector Architecture

Collectors retrieve raw information.

Adapters interpret it.

These are separate concepts.

```text
Collector
    ↓
Raw source data
    ↓
Adapter
    ↓
Universal Event

```

Collector types:

### Filesystem collector

Watch known directories for:

- JSONL
- SQLite
- JSON
- logs
- metadata

### Process collector

Detect running agent processes where useful.

### Hook collector

Accept events emitted directly by an agent.

### API collector

Use local APIs exposed by agents.

### Import collector

Import historical data manually.

# 18. Adapter Interface

Conceptually:

```go
type Adapter interface {
    ID() string
    Name() string

    Detect(ctx context.Context) (bool, error)

    Sources() []Source

    Collect(ctx context.Context, source Source) ([]Event, error)

    Watch(ctx context.Context, source Source, emit func(Event)) error
}

```

Adapters should be independently testable.

An adapter must not contain dashboard-specific logic.

# 31. Performance Requirements

The dashboard should remain responsive with large datasets.

Target:

```text
1M events      → normal
10M events     → normal
100M events    → supported with optimization

```

No artificial event limit should exist.

Optimization strategy:

1. SQLite WAL
2. proper indexes
3. batch inserts
4. prepared statements
5. time-bucketed analytics
6. background aggregation only when necessary
7. pagination
8. streaming responses

Do not prematurely build a distributed storage system.

# 33. Data Integrity

Every imported event should be idempotent.

If the same source event is encountered twice:

```text
event ID → deduplicate

```

Where an upstream event has no stable ID, derive a deterministic ID from source metadata.

Never double-count tokens because a collector restarted.

---

# 34. Privacy

Local-first does not automatically mean privacy-safe.

The application must explicitly consider sensitive data.

Do not collect:

- API keys
- passwords
- authentication cookies
- secrets
- environment variables

Avoid storing:

- full prompts by default
- full tool arguments by default
- full tool results by default
- source-code contents

Where data could contain secrets, provide configurable redaction.

---

# 35. Security

```text

```

No authentication should be required for the default local-only server.

# 44. UX Principles

The dashboard should be:

### Dense

Developers want information, not giant marketing cards.

### Fast

Graphs should render quickly even with years of history.

### Inspectable

Every aggregate number should be traceable back to events.

For example:

```text
12.4M tokens

```

should be clickable and reveal the underlying sessions/events.

### Local

No:

```text
"Create an account"
"Connect your workspace"
"Start free trial"

```

The application starts immediately.

### Honest

If a metric is unavailable from an agent:

```text
Reasoning tokens
Unavailable for this source

```

Never estimate it and present it as fact.

# 57. Plugin Architecture

Long-term, adapters should be loadable without modifying the core.

Possible model:

```text
mtrx
    ├── core
    ├── built-in adapters
    └── external adapters

```

However, avoid Go plugins initially because portability and deployment complexity are poor.

Prefer:

- external adapter processes
- JSONL
- HTTP
- Unix sockets

This preserves the single-binary core while allowing extensibility.
